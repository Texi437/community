# 阶段性开发问题整理

整理日期：2026-11-28  
项目：邻里共治

本阶段围绕 Android 居民端、Java 后端与 MySQL 的本地联调，处理了接口访问受阻、数据库实例混用、中文路径兼容和数据库进程管理问题。形成的运行方式是：Android 通过 ADB 端口转发访问本机后端，项目数据库使用独立端口，并由 Windows 服务管理。

本文合并《数据库连接故障与修复记录.md》和《development_issues_and_solutions.md》，按问题及处理结论组织。配置说明已与阶段源码核对；连接与服务运行结果引用原记录，不将文档整理视为重新执行全部功能测试。

## 一、联调环境

| 组件 | 本阶段配置 | 作用 |
|---|---|---|
| Android 客户端 | Java/XML，后端地址 `http://127.0.0.1:8080` | 居民端界面与业务操作 |
| ADB 转发 | `tcp:8080` 转发至宿主机 `tcp:8080` | 连接模拟器与本机后端 |
| Java 后端 | Spring Boot，监听 `127.0.0.1:8080` | 提供业务接口并访问数据库 |
| 项目数据库 | MySQL 8.4.13，`127.0.0.1:3307` | 保存 `linli_governance` 业务数据 |
| 项目数据库服务 | `LinliMySQL`，原记录验收为自动启动 | 管理项目 MySQL 的运行 |
| 系统数据库 | `MySQL80`，端口 `3306` | 服务于其他本机项目 |

`linli_governance` 在验收记录中共 17 张表，包括 16 张业务表和 1 张迁移账本表。系统实例与项目实例的数据目录独立，连接时须同时确认端口、库名和账号。

## 二、Android 与后端连接问题

### 1. HTTP 请求受到明文流量策略限制

**问题。** 本地后端使用 HTTP，客户端出现请求无法发出的情况。

**原因。** 明文访问策略与应用的目标 API 及网络配置有关。目标 API 为 28 及以上的应用，`usesCleartextTraffic` 默认值为 `false`，不能概括成“Android 9 以上会拦截所有 HTTP 请求”。[Android 清单属性说明](https://developer.android.com/guide/topics/manifest/application-element#usesCleartextTraffic)

**处理。** 联调阶段显式允许 HTTP。当前阶段源码的 `android/app/src/main/AndroidManifest.xml` 与 `android/app/src/debug/AndroidManifest.xml` 均设置了：

```xml
android:usesCleartextTraffic="true"
```

**配置结论。** 现有代码满足本地 HTTP 联调需要，但该设置目前也位于主清单中。发布配置收敛列入后续工作：默认关闭明文访问，在调试变体按需开启，并验证发布构建使用 HTTPS。

### 2. 模拟器与电脑的回环地址含义不同

**问题。** App 使用 `http://127.0.0.1:8080` 时，未建立转发便无法访问电脑上的服务。

**原因。** 模拟器中的 `127.0.0.1` 指向模拟器自身。Android Emulator 的 `10.0.2.2` 是宿主机回环地址的别名，因此后端绑定 `127.0.0.1` 本身不能证明 `10.0.2.2` 必然不可达。原记录中的超时现象，不足以确定其具体原因。[Android 模拟器地址说明](https://developer.android.com/studio/run/emulator-networking-address)

**处理。** 本阶段统一使用 ADB 反向端口转发，保持 App 与后端使用明确的本机地址：

```powershell
adb devices
adb reverse tcp:8080 tcp:8080
adb reverse --list
```

`android/gradle.properties` 中保留：

```properties
backendUrl=http://127.0.0.1:8080
```

转发建立后，App 对设备端 `8080` 的访问经 ADB 传送至电脑端 `8080`。后端继续监听 `127.0.0.1`。修改构建地址后，需要同步、重新构建并安装 App；设备连接或 ADB 重启后，重新检查转发。存在多个设备时，通过 `adb -s 设备编号` 指定目标。

**验证结论。** 原联调记录采用该方案恢复了客户端访问后端的连接路径。后续排查分别检查后端是否运行、设备是否在线、转发是否存在及 App 构建地址，避免把不同层次的问题混为一谈。

## 三、数据库连接与运行管理问题

### 3. DBeaver 连接被拒绝

**问题。** DBeaver 报错：

```text
[08S01] Communications link failure
Connection refused: getsockopt
```

**原因。** 当次检查发现 `3307` 没有监听进程，项目 MySQL 实例未运行。请求在 TCP 建连阶段失败，尚未进入数据库身份验证；该次故障不由密码错误引起。

**处理。** 启动项目数据库，保留原连接参数：主机 `127.0.0.1` 或 `localhost`、端口 `3307`、数据库 `linli_governance`、账号 `linli_app`。密码从本机 `.local` 配置读取，不写入提交文档。

**验证结果。** 原记录使用 JDBC 分别连接 `localhost` 与 `127.0.0.1`，均返回 MySQL 8.4.13，用户为 `linli_app@127.0.0.1`，可读取 17 张表。

### 4. 系统 MySQL 与项目 MySQL 容易混用

**问题。** 系统 `MySQL80` 正在运行，容易被误认为项目数据库已经启动。

**原因。** 系统服务监听 `3306`，项目实例监听 `3307`；当次排查确认系统实例中没有项目业务库。把客户端端口直接改成 `3306`，不会恢复对项目数据的访问。

**处理与结论。** 使用项目的 `3307` 连接；系统 `MySQL80` 保持原用途。实例定位以端口、数据目录和库名共同确认，不能只看“已有 MySQL 服务在运行”。

### 5. 中文路径导致 MySQL 客户端读取配置失败

**问题。** 配置文件存在，但命令行仍提示：

```text
Failed to open required defaults file
Fatal error in defaults handling. Program aborted.
```

**原因与处理。** 本机记录显示，MySQL 客户端在读取中文目录下的配置时出现兼容问题。项目通过 ASCII 目录联接 `D:\linli-dev` 访问同一份后端文件，手工命令也使用该入口，例如：

```powershell
& "D:\linli-dev\.tools\mysql-8.4.13-winx64\bin\mysql.exe" `
  "--defaults-extra-file=D:\linli-dev\.local\mysql-app.cnf" `
  linli_governance
```

**验证结论。** 原记录通过联接路径完成连接。`server/scripts/env.ps1` 已包含非 ASCII 项目路径的入口选择逻辑。目录联接指向原目录，不是另一份数据库；迁移电脑时应根据新路径配置，不能机械照搬本机路径。

### 6. 手动启动的数据库进程未持续运行

**问题。** 数据库一度连接成功，之后再次出现连接被拒。检查发现监听端口与 `mysqld` 进程均已消失，日志末尾没有正常关闭记录。

**原因判断。** 这些现象确认了数据库进程已退出，但不能单凭日志尾部确定终止来源。原记录提出会话进程回收的解释；最终处理聚焦于让数据库脱离临时会话，建立独立的服务管理方式。

**处理。** 本机将项目 MySQL 注册为独立 Windows 服务 `LinliMySQL`，使用项目的配置与数据目录，并设为自动启动。Windows 服务可通过系统服务管理器启动、停止及设置启动方式。[MySQL Windows 服务说明](https://dev.mysql.com/doc/refman/8.4/en/windows-start-service.html)

**验证结果。** 原记录显示服务状态为 `Running`、启动类型为 `AUTO_START`，监听 `127.0.0.1:3307`，业务账号可连接并读取 17 张表。该结果确认了当次服务化配置与数据访问；“自动启动已配置”不等同于已经完成重启电脑后的复测。

日常使用 Windows“服务”界面管理 `LinliMySQL`。命令行查看状态可执行：

```powershell
Get-Service LinliMySQL | Select-Object Status, StartType
```

服务化是本机环境变更，当前源码中的安装及启停脚本并未因此自动变成服务管理脚本。新电脑仍需按项目 README 初始化环境，再按需要配置服务。

### 7. 服务化后的 PID 记录与启停职责需要统一

**问题。** 手动启动遗留的 `.runtime/mysql-process.id` 可能不再对应当前数据库进程。

**处理。** 原记录在改由服务管理后清理了过期 PID 文件。日常数据库启停交给服务管理器，避免混用旧 PID 与服务状态。

**源码核对。** 当前脚本行为如下：

| 脚本或参数 | 实际行为 | 服务化后的使用方式 |
|---|---|---|
| `start-db.ps1` | 端口已监听时用业务账号执行查询；连接成功后返回。端口未监听时直接启动 `mysqld` 进程 | 先启动 `LinliMySQL`，再复用连接检查，避免又进入手动进程模式 |
| `start.ps1` | 调用数据库启动检查，随后启动后端 | 数据库服务运行后用于启动后端 |
| `stop.ps1 -KeepDatabase` | 保留数据库，仅处理脚本记录的后端进程 | 修改后端代码时采用此方式 |
| `stop.ps1` | 默认还会通过 `mysqladmin shutdown` 关闭数据库 | 会影响正在运行的项目数据库服务，之后需重新启动服务 |

后端进程记录校验包含路径和启动时间；MySQL PID 分支校验的是可执行文件路径，两者不能混写为同一套身份校验。IntelliJ IDEA 启动的后端应在 IDEA 中停止，不能假定项目脚本已记录并接管该进程。

## 四、分层检查顺序

1. **数据库服务。** 查看 `LinliMySQL` 状态，再检查 `3307` 是否监听。
2. **数据库连接。** 确认连接项目实例，校验库名及业务账号，读取业务表。
3. **后端服务。** 检查 `127.0.0.1:8080` 的健康接口，再定位数据库或业务错误。
4. **模拟器通道。** 查看 `adb devices` 与 `adb reverse --list`，确认目标设备和端口映射。
5. **客户端配置。** 核对后端地址、明文访问策略，以及设备上是否安装了最新构建。
6. **业务操作。** 连接恢复后，再验证登录、资料、工单和活动等流程。

当前 `server/scripts/check.ps1` 可检查数据库连接、后端健康状态和未登录访问本人资料时的 `401` 响应。该检查用于确认基础连接与访问保护，业务操作仍按相应功能场景验证。

## 五、阶段成果与后续工作

本阶段明确了客户端、后端与数据库各自的连接边界，统一了本地联调入口，并形成数据库服务化管理方式。后续开发可沿上述分层路径定位问题，减少反复改端口、改密码和重启整套环境的试错。

下一阶段继续完善推荐算法、业务数据和前端界面，同时补齐发布构建的 HTTPS 配置、数据库服务与脚本的管理约定，以及重启和设备重连后的验证。本文作为阶段问题记录随源码维护，不代表产品功能与界面设计已经定稿。
